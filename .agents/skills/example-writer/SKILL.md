# Documentation Example Writer

Guide for writing and editing the example programs in `Documentation/Examples/`.
The examples are compiled and run by the `documentation` CMake target,
their sources and outputs are shown in the API documentation
and in the users' guide,
so they must compile, run and be easy to read.
For the Doxygen comments that reference the examples,
see the `doxygen-writer` skill.

## File layout

- The `.cpp` file is the **only** real source file.
  Always edit the `.cpp` file.
  The same source must compile with the host compiler, `nvcc` and `hipcc`.
- The `.cu` and `.hip` variants are going to be generated by CMake
  and removed from the repository.
  Until then, the existing examples have `.cu` (and in some directories `.hip`)
  symbolic links to the `.cpp` file,
  and the CMake files compile the `.cu` link in CUDA builds.
  A new example needs the same links as its neighbours:
  ```bash
  ln -s ArrayExample.cpp ArrayExample.cu
  ```
  Never put code into a `.cu` or `.hip` file.
- Name the file after the documented class or function,
  e.g. `ArrayExample_forElements.cpp`, `GraphExample_VertexView.cpp`,
  `SegmentsExample_forElements.cpp`.
- A larger example may keep its code in a `.h` file
  with one-line `#include` wrappers in `.cpp` and `.cu`
  (see `Solvers/ODE/`).
  Use this only when the directory already does so.

## CMake registration

Every example must be registered in the `CMakeLists.txt` of its directory,
otherwise it is never compiled and silently rots.
Add the target name to the list of examples (e.g. `COMMON_EXAMPLES`)
which is built from `.cu` when `TNL_BUILD_CUDA` is on and from `.cpp` otherwise,
and whose output is written to
`${TNL_DOCUMENTATION_OUTPUT_SNIPPETS_PATH}/<target>.out`
(adapted from `Documentation/Examples/Graphs/CMakeLists.txt`):

```cmake
set(COMMON_EXAMPLES
    GraphExample_Constructors
    GraphExample_setEdges
)

if(TNL_BUILD_CUDA)
    foreach(target IN ITEMS ${COMMON_EXAMPLES})
        add_executable(${target} ${target}.cu)
        ...
```

The `.out` files are generated, never committed.
Format CMake files with `gersemi`.

## Program structure

- Write the example body as a function template over `Device`
  and call it from `main` for every backend:
  ```cpp
  template< typename Device >
  void
  vertexViewExample()
  {
     ...
  }

  int
  main()
  {
     std::cout << "Running on host:\n";
     vertexViewExample< TNL::Devices::Host >();

  #ifdef __CUDACC__
     std::cout << "\nRunning on CUDA device:\n";
     vertexViewExample< TNL::Devices::Cuda >();
  #endif

  #ifdef __HIP__
     std::cout << "\nRunning on HIP device:\n";
     vertexViewExample< TNL::Devices::Hip >();
  #endif

     return EXIT_SUCCESS;
  }
  ```
- Lambdas executed on the device are `__cuda_callable__`.
- Include exactly the headers the example uses (TNL headers in angle brackets).
- Print the result after every documented call with `std::cout`,
  so the generated `.out` file shows the expected output.

## Naming

Examples are read by people new to TNL,
so use full, descriptive names of variables and lambda parameters.
Never use abbreviations or single letters:

| Use | Not |
|-----|-----|
| `vertex` | `v` |
| `weight` | `w` |
| `source`, `target` | `src`, `tgt`, `dst` |
| `index` | `idx`, `i` (except in trivial loops) |
| `value` | `val` |
| `distances`, `predecessors` | `dist`, `pred` |

Unused lambda parameters may be left unnamed.
Apply the same rule to comments and output strings
(`weight <= 3`, not `w<=3`).

## Snippets

Doxygen `\snippet` directives include named blocks of the example:

```cpp
   //! [traversing-1]
   ...
   //! [traversing-1]
```

```markdown
\snippet Algorithms/Segments/SegmentsExample_forElements.cpp traversing-1
```

Rules:

- Every snippet is **self-contained**:
  it declares all lambdas, index arrays and output vectors
  needed by the call it documents,
  so a reader of one snippet does not have to look at the others.
- Pass lambdas and index arrays inline as arguments
  instead of naming them in an earlier snippet.
  Only output vectors need unique names
  (e.g. `distancesEdge`, `distancesInduced`).
- Put a short comment before each lambda naming its role:
  `// edge predicate`, `// vertex predicate`, `// edge weight callable`,
  `// visitor`.
- Each snippet ends with the `std::cout` line printing its result.
- A shared definition block with type aliases
  (e.g. `GraphType`, `IndexType` and `VectorType`)
  is the only exception; define it once near the top of the file.
- When all variants of one algorithm are shown in one file,
  use one input rich enough to give distinct outputs for every variant
  (isolated vertices, branches, edges the predicate can filter out).

Use `\include <file>.cpp` with `\include <target>.out`
when the whole program is shown.

## Formatting

Format the sources with:

```bash
just format
```

Do not use `// clang-format off` / `// clang-format on` comments
unless explicitly told to do so.

## Verification checklist

- [ ] All code is in the `.cpp` file; `.cu` (and `.hip` where the neighbours have it)
      are only symlinks to it, until CMake generates them.
- [ ] The target is registered in `CMakeLists.txt`.
- [ ] The example builds and runs in a host build and in a CUDA or HIP build.
- [ ] `main` runs the example on Host and, under `__CUDACC__` / `__HIP__`, on the GPU.
- [ ] Variable and parameter names are not abbreviated.
- [ ] Every `//! [name]` snippet is self-contained and ends with printed output.
- [ ] Every `\snippet` / `\include` in the headers and the users' guide
      points to an existing file and block name.
- [ ] `just check` passes (checks formatting, linting, typos)
