# Matrix Assembly Benchmark

Performance benchmark of sparse matrix assembly in TNL, Ginkgo, Hypre, PETSc and cuSPARSE on CPU and GPU.
The benchmark assembles the matrices of two kinds of problems and measures the time for the allocation
of the matrix and for filling it with the non-zero elements.

## Test problems

The problem is selected by `--problem` (`laplace`, `graph` or `all`).

### Laplace operator

The matrix corresponds to the 3-, 5- or 7-point stencil of the Laplace operator discretized by the finite
difference method on a structured grid in 1D, 2D or 3D with `x-size`, `y-size` and `z-size` nodes along the axes.
Grid nodes are numbered lexicographically.
Boundary nodes give Dirichlet rows with a single unit diagonal element, otherwise all rows have the same length.

The default grid sizes are 10^6 nodes in 1D, 1000x1000 nodes in 2D and 100x100x100 nodes in 3D.

### Graph Laplacian

The matrix is the regularized Laplacian `L = D - A + I` of a random undirected graph, where `A` is the
adjacency matrix and `D` is the diagonal matrix of the vertex degrees.
Row `i` contains the diagonal element `deg(i) + 1` and `-1` for each neighbor of the vertex `i`,
so the length of the row is `deg(i) + 1`.

The graph is generated by the R-MAT generator with the parameters of the Graph500 benchmark
(`a = 0.57`, `b = c = 0.19`, `d = 0.05`).
It has `2^graph-scale` vertices and `graph-edge-factor * 2^graph-scale` generated edges,
self-loops and multiple edges are removed.
The vertices are randomly permuted, so the long rows are spread over the whole matrix.
The degrees follow a power law distribution, so unlike the Laplace operator, the lengths of the rows
differ by several orders of magnitude.
For example, the default graph (`--graph-scale 20 --graph-edge-factor 8`) gives a matrix with
1 048 576 rows and 17 134 914 non-zero elements, the row lengths are between 1 and 39 752:

| Row length    | 1–9     | 10–99   | 100–999 | 1000–9999 | ≥ 10000 |
|---------------|---------|---------|---------|-----------|---------|
| Number of rows | 878 737 | 148 128 | 20 360  | 1 330     | 21      |

The graph is generated on the host before the measurement (and copied to the GPU in GPU builds).
Its adjacency lists are the input of the assembly, i.e. each row is assembled from the list of neighbors
of the vertex.

## Measured operations

- `allocation` – everything that can be done before the values of the matrix elements are known.
  This includes setting the dimensions, computing the row capacities and allocating the memory.
- `filling` – writing the non-zero elements into an allocated matrix, including any finalization
  required by the library.
- `assembly` – allocation and filling together.
  This is the fairest comparison of the libraries, because each library splits the work between
  the two phases differently.

For GPUs, the assembly on the host followed by the transfer of the matrix to the GPU is measured as well.
This is done for all libraries:

- `host assembly` – assembling the matrix on the host.
- `transfer` – copying the matrix assembled on the host to the GPU.
- `host assembly + transfer` – both together.
  Compare it with `assembly` on the GPU to see the benefit of assembling the matrix directly on the GPU.

| Library  | Host assembly | Transfer |
|----------|---------------|----------|
| TNL      | the same format on the host | assignment operator of `TNL::Matrices::SparseMatrix` |
| Ginkgo   | the same format on the OpenMP executor | `copy_from` |
| Hypre    | IJ matrix in the host memory | `HYPRE_IJMatrixMigrate` |
| PETSc    | `MATSEQAIJ` (CSR only) | `MatConvert` to `MATSEQAIJCUSPARSE` and forcing the copy to the GPU |
| cuSPARSE | CSR arrays on the host | copying the arrays and creating the matrix descriptor |

For TNL, the operation `array transfer` measures copying only the arrays of values and column indexes,
which is the lower bound of the transfer time.

The GPU executable is built with OpenMP for the host code (TNL does not enable OpenMP for code compiled
by nvcc by default), so the host assembly runs in parallel as in the host executable.

Only bulk assembly is benchmarked, not inserting the elements one by one.

## Libraries and formats

| Library  | CSR | Ellpack | SlicedEllpack | Assembly method |
|----------|-----|---------|---------------|-----------------|
| TNL      | `CSR` | `Ellpack` | `SlicedEllpack` | `setRowCapacities` and `forAllRows` with row views |
| Ginkgo   | `Csr` | `Ell` | `Sellp` | COO triplets in `gko::device_matrix_data` and `read` |
| Hypre    | ParCSR | – | – | IJ interface with one `HYPRE_IJMatrixSetValues2` call for all rows |
| PETSc    | `MATSEQAIJ`, `MATSEQAIJCUSPARSE` | – | `MATSEQSELL`, `MATSEQSELLCUDA` | `MatSetPreallocationCOO` and `MatSetValuesCOO` |
| cuSPARSE | CSR | – | – | COO triplets and `cusparseXcoo2csr` |

TNL is benchmarked with all segments supported by `TNL::Matrices::SparseMatrix`:
`CSR`, `AdaptiveCSR`, `Ellpack`, `SlicedEllpack`, `ChunkedEllpack`, `BiEllpack`
and the sorted variants of all of them (`SortedCSR`, `SortedAdaptiveCSR`, `SortedEllpack`,
`SortedSlicedEllpack`, `SortedChunkedEllpack`, `SortedBiEllpack`), which reorder the segments by their sizes.
The segments use the default organization of the elements for the device (row-major on the host,
column-major on GPUs).
The other libraries are benchmarked only with the formats from the table above.

Notes:

- cuSPARSE is benchmarked only in CUDA builds, the hipSPARSE variant for HIP builds is not implemented yet.
- cuSPARSE has no matrix assembly routine.
  The COO triplets are generated by a TNL kernel and converted to CSR with `cusparseXcoo2csr`.
- For the libraries assembling the matrix from COO triplets (Ginkgo, PETSc, cuSPARSE) and for Hypre,
  the triplets are generated on the target device by a TNL kernel.
  They are generated in the row-major order, so no sorting is needed.
- In PETSc, the COO row and column indexes are set on the host during `allocation`.
  Only the values are generated on the device during `filling`.
- PETSc has no native COO assembly for the SELL format.
  The generic implementation is used, so the SELL matrix is also preallocated with the row lengths.
  The generic implementation reads the values on the host, so they are generated on the host even for
  `MATSEQSELLCUDA`.
- `Ellpack` and `SortedEllpack` (and Ginkgo `Ell`) pad all rows to the length of the longest row.
  If the padded matrix does not fit into the index type, the format is skipped with an error message.
  This is the case of the default graph problem.
- Hypre and PETSc run on a single MPI rank.
- Hypre and PETSc support only the precision and the device they were built for.
  Other combinations are skipped.
  The host executable must be linked with a CPU build of Hypre and the GPU executable with a GPU build.

## Correctness

With `--verify true` (the default), each assembled matrix is copied to the host and compared with the
exact matrix after the measurement.
Failures are reported as error messages.

## Building

The external libraries are optional.
They are enabled when they are found by CMake:

| Library  | CMake variable | Notes |
|----------|----------------|-------|
| Ginkgo   | `Ginkgo_DIR` or `CMAKE_PREFIX_PATH` | |
| PETSc    | `PKG_CONFIG_PATH` or `CMAKE_PREFIX_PATH` | found by pkg-config, requires MPI |
| Hypre    | `HYPRE_ROOT` | CPU build used by the host executable, requires MPI |
| Hypre    | `HYPRE_GPU_ROOT` | CUDA or HIP build used by the GPU executable, requires MPI |

Example:

```bash
PKG_CONFIG_PATH=$HOME/.local/petsc-cuda/lib/pkgconfig \
cmake --preset toolchain-gcc-nvcc -B build/release-cuda -DCMAKE_BUILD_TYPE=Release \
   -DHYPRE_ROOT=/usr -DHYPRE_GPU_ROOT=$HOME/.local/hypre-cuda
cmake --build build/release-cuda --target tnl-benchmark-matrix-assembly tnl-benchmark-matrix-assembly-cuda
```

A GPU build of PETSc (e.g. `--with-cuda`) can be used by both executables, a CPU build of PETSc only by
the host executable.
The CPU and GPU builds of Hypre usually have the same soname, so the directory of the selected build is
put at the beginning of the runtime search path of each executable.

Notes on building the libraries with CUDA 13:

- Hypre 3.x requires Umpire for GPU builds unless it is configured with `-DHYPRE_ENABLE_UMPIRE=OFF`.
  Without Umpire, Hypre allocates the memory directly (like the other libraries), which is preferable
  for this benchmark.
- Hypre 3.2.1 does not compile with CCCL 3.5 (CUDA 13.4) because of
  `cuda::std::reverse_iterator< thrust::device_ptr< T > >` in `src/IJ_mv/IJ*_parcsr_device.c`.
  Passing raw pointers instead of `thrust::device_pointer_cast( ... )` to `thrust::make_reverse_iterator`
  fixes the build.

## Usage

```bash
tnl-benchmark-matrix-assembly-cuda --device all --problem laplace --dimension 2 --x-size 2000 --y-size 2000 \
   --libraries TNL Ginkgo --formats CSR SlicedEllpack --log-file assembly.json
tnl-benchmark-matrix-assembly-cuda --device all --problem graph --graph-scale 21 --log-file assembly.json
```

Main options:

- `--problem` – `laplace`, `graph` or `all`.
- `--dimension` – `1`, `2`, `3` or `all` (Laplace problem).
- `--x-size`, `--y-size`, `--z-size` – numbers of grid nodes along the axes (0 means the default size).
- `--graph-scale` – the graph has `2^graph-scale` vertices (default 20).
- `--graph-edge-factor` – number of generated edges per vertex (default 8).
- `--graph-seed` – seed of the random generator of the graph (default 0).
- `--libraries` – any of `TNL`, `Ginkgo`, `Hypre`, `PETSc`, `cuSPARSE` or `all`.
- `--formats` – any of the formats listed above or `all`.
- `--precision` – `float`, `double` or `all`.
- `--device` – `host`, `cuda`, `hip` or `all`.
- `--verify` – verify the assembled matrices.

## Processing the results

The script `process-results.py` reads one or more JSON log files and writes an HTML page with tables
of the measured times and LaTeX/TikZ (pgfplots) figures with speed-up graphs:

```bash
./process-results.py host.json gpu.json --output-dir results --pdf
```

- `matrix-assembly.html` – tables of all measured times and the speed-up of TNL for the assembly,
  for each device and precision.
- `tnl-formats-<device>-<precision>.tex` – assembly time of the TNL formats relative to TNL `CSR`
  for all problems.
- `speedup-<operation>-<device>-<precision>.tex` – speed-up of TNL over the other libraries with the
  same matrix format for the allocation, filling and assembly.
- `gpu-speedup-<device>-<precision>.tex` – speed-up of the assembly on the GPU over the assembly on
  the host followed by the transfer, for all libraries and formats.
- `host-to-gpu-<device>-<precision>-<problem>.tex` – stacked bars with the times of the host assembly and
  the transfer for all libraries and formats.

The `--pdf` option compiles the figures with `pdflatex`.
The script requires `pandas`.
